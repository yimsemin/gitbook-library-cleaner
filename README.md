# GitBook 미사용 이미지 정리

GitBook 스페이스의 Library에 쌓인 **아무 데서도 쓰지 않는 이미지**를 AI 에이전트가 대신 찾아 지우는 스킬입니다. GitBook 편집자를 위한 도구입니다.

- 파일을 하나씩 열어 보지 않고, 지울 수 있는 이미지의 목록과 용량을 받습니다.
- **승인한 파일만** Change Request(검토 후 병합하는 변경 묶음) 안에서 삭제합니다. 병합하기 전까지 게시본은 바뀌지 않습니다.
- 삭제할 때마다 빠진 파일과 깨진 참조가 없는지 다시 검사합니다.

[설치](#설치)한 뒤 에이전트에게 이렇게 요청합니다.

> GitBook 미사용 이미지 정리해줘. 스페이스는 `https://app.gitbook.com/o/…/s/…/`, 삭제는 Change Request #12에서 하고 병합은 하지 마.

Windows의 Claude Code와 Chrome으로 실제 스페이스에서 170여 개 삭제를 확인했습니다. 다른 환경은 [검증 상태](#검증-상태)를 보세요.

## 시작하기 전에

| 필요한 것 | 내용 |
|---|---|
| 에이전트 | 내 컴퓨터에서 명령을 실행하고, 브라우저에서 JavaScript를 실행할 수 있어야 합니다 |
| Node.js | 24 이상 |
| 브라우저 | GitBook에 로그인되어 있고 화면 언어가 영어여야 합니다 |
| GitBook 권한 | 대상 스페이스의 편집 권한 |
| Change Request | 삭제를 담을 초안 또는 열린 상태의 것. 번호를 확인해 둡니다 |

### 설치

`skill` 폴더를 에이전트의 스킬 폴더에 `gitbook-library-cleaner`라는 이름으로 복사합니다. `node_modules`와 `gblc-reports`는 복사하지 않습니다.

| 에이전트 | 일반적인 스킬 폴더 |
|---|---|
| Claude Code | `~/.claude/skills/` |
| Codex | `~/.agents/skills/` |

Codex는 삭제할 때 설정의 **Browser > Developer mode > Enable full CDP access**가 필요합니다. 브라우저 내부 기능까지 여는 위험이 큰 설정이므로, 정리를 마치면 끄는 것을 권장합니다.

## 기술 기반

GitBook에서 확인한 공식 API와 CLI에는 파일 삭제 기능이 없습니다. 그래서 읽기와 삭제의 방법이 다릅니다.

| 맡는 일 | 방법 |
|---|---|
| 진행과 안내 | 에이전트가 [SKILL.md](skill/SKILL.md)의 절차를 따릅니다 |
| 읽기와 판정 | Node.js 스크립트가 GitBook API를 조회하고, 사용 여부를 코드로 판정합니다. 로그인은 공식 GitBook CLI(`@gitbook/cli`)의 것을 씁니다 |
| 삭제 | 로그인된 브라우저의 GitBook 화면에서 스크립트가 삭제 메뉴를 파일마다 대신 누릅니다 |

에이전트의 대화에는 요약만 들어갑니다. 페이지 본문과 전체 파일 목록은 스크립트가 처리합니다.

## 이용 순서

**준비 → 요청 → 검사 → 승인 → 재검사 → 삭제 → 검증 → 병합**. 재검사부터 검증까지는 에이전트가 이어서 진행하며, 파일이 많으면 묶음으로 나눠 삭제와 검증을 반복합니다.

사용자가 직접 하는 일은 **로그인 승인(처음 한 번), 요청, 삭제 목록 승인, 병합**입니다.

### 1. 준비 (처음 한 번)

- **진행**: 에이전트가 필요한 패키지를 설치하고 로그인 명령을 실행합니다.
- **기술**: `npm ci`, GitBook CLI의 브라우저 로그인.
- **사용자가 할 일**: 열린 GitBook 화면에서 로그인을 승인합니다.
- **바뀌는 것**: 스킬 폴더에 `node_modules`가 생기고, 내 컴퓨터에 로그인 정보가 저장됩니다. GitBook 콘텐츠는 그대로입니다.
- **주의**:
  - 브라우저 승인으로 저장되는 권한에는 콘텐츠 쓰기, 병합, 게시, 구성원·권한 변경이 포함됩니다. 이 도구는 조회 요청만 보냅니다.
  - 권한을 조회로 좁히려면 [개발자 설정](https://app.gitbook.com/account/developer)에서 `Read only` 토큰을 만들고, 스킬 폴더의 터미널에서 `node node_modules/@gitbook/cli/cli.js auth`를 실행해 입력합니다. 토큰은 대화에 붙여 넣지 않습니다.
  - Windows에서는 `client_id` 오류 탭이 함께 열릴 수 있습니다. 그 탭은 닫고 다른 탭에서 승인합니다.

### 2. 요청

- **진행**: 에이전트가 대상을 확인합니다.
- **사용자가 할 일**: 스페이스 주소와 Change Request 번호를 알려 줍니다. 번호 없이 요청하면 본문을 기준으로 보고만 받습니다.
- **바뀌는 것**: 없습니다.
- **주의**: Change Request에서 하던 편집은 끝낸 뒤에 요청합니다. 방금 올려 아직 페이지에 넣지 않은 이미지는 삭제 후보가 됩니다.

### 3. 검사

- **진행**: 모든 파일을 사용 여부에 따라 나누고, 삭제 후보의 개수·용량·목록 파일을 알려 줍니다. 아무것도 지우지 않는 시험 실행(Dry run)입니다.
- **기술**: `scan` 명령. 대상 스페이스와 조직의 다른 스페이스, 병합되지 않은 Change Request, 사이트 설정을 읽습니다([판정 기준](#판정-기준)).
- **사용자가 할 일**: 기다립니다. 문서 133개와 다른 스페이스 4개를 검사하는 데 약 10초 걸렸습니다.
- **바뀌는 것**: 명령을 실행한 위치의 `gblc-reports/<시각>/`에 `candidates.tsv`(삭제 후보)와 `report.json`(전체 판정)이 생깁니다. GitBook은 그대로입니다.
- **주의**:
  - 검사 중에 누가 내용을 바꾸거나 읽지 못한 항목이 있으면 "검사 불완전"이 되어 삭제할 수 없습니다. 편집이 끝난 뒤 다시 검사합니다.
  - 이 규모의 검사 한 번은 API 요청 약 230건을 씁니다. 재검사와 검증도 전체 검사이므로 파일이 많으면 계정의 API 호출 제한에 걸릴 수 있습니다. "호출 제한" 오류가 나면 안내된 시간 뒤에 다시 실행합니다.
  - 보고서에는 내 문서에서 나온 정보가 들어 있습니다. 공유하거나 저장소에 올리지 않습니다.

### 4. 승인

- **진행**: 에이전트가 삭제 목록과 한계를 보여 주고 승인을 기다립니다.
- **기술**: 승인 ID. 스페이스, Change Request, 삭제 목록이 모두 같을 때만 다음 단계가 받아들입니다.
- **사용자가 할 일**: `candidates.tsv`를 열어 확인하고, 전부 또는 일부를 승인합니다.
- **바뀌는 것**: 없습니다.
- **주의**: 아래는 도구가 알 수 없으므로 직접 확인해야 합니다.
  - 외부 웹페이지, 메일 등 GitBook 밖에서 주소를 직접 쓰는 이미지
  - 내 계정으로 볼 수 없는 스페이스나 다른 조직에서 쓰는 이미지
  - 지금은 안 쓰지만 병합이 끝난 과거 버전에서 쓰던 이미지(삭제 후보가 됩니다)

### 5. 삭제 직전 재검사

- **진행**: 전체를 다시 검사하고 이번에 지울 묶음을 만듭니다. 승인한 파일에 새 참조가 생겼으면 중단합니다.
- **기술**: `prepare` 명령. 같은 보고서 폴더에 삭제 스크립트와 검증 기준(`delete.js`, `next.js`, `pending.json`)을 만듭니다.
- **사용자가 할 일**: 기다립니다.
- **바뀌는 것**: 내 컴퓨터의 파일만 생깁니다.
- **주의**: 이 컴퓨터에서 처음 삭제한다면 파일 2개짜리 묶음으로 먼저 시험하고, 이후 20개씩 진행합니다. 남은 API 호출이 다음 검증에 모자라면 묶음을 만들지 않고, 다시 실행할 시각을 알려 줍니다.

### 6. 삭제

- **진행**: 에이전트가 해당 Change Request의 편집 화면에서 Library > Images를 목록 보기로 열고 스크립트를 실행합니다.
- **기술**: 페이지에서 실행하는 JavaScript. 지정한 Change Request의 화면에서만 시작하고, 파일 ID가 일치하는 항목만 하나씩 삭제합니다.
- **사용자가 할 일**: 브라우저 로그인을 유지하고 기다립니다. 에이전트가 브라우저 사용 허락을 요청하면 결정합니다.
- **바뀌는 것**: **Change Request에서 파일이 삭제됩니다.** 게시본은 그대로입니다. 파일당 약 4초 걸립니다.
- **주의**:
  - 삭제 중에는 그 Change Request를 편집하거나 화면을 이동하지 않습니다.
  - 화면이나 확인 창이 예상과 다르면 스크립트가 멈춥니다. 직접 눌러 이어서 지우지 말고 에이전트의 보고를 따릅니다.

### 7. 검증과 반복

- **진행**: 승인한 파일이 지워졌는지, 다른 파일이 함께 지워지지 않았는지, 깨진 참조가 없는지, 본문이 바뀌지 않았는지 확인합니다. 통과하면 다음 묶음으로 6단계를 반복합니다.
- **기술**: `verify --next` 명령. GitBook에 삭제가 반영되기를 기다린 뒤 전체를 다시 검사합니다.
- **사용자가 할 일**: 끝날 때까지 기다리고 결과 보고를 확인합니다.
- **바뀌는 것**: 반복하는 동안 Change Request의 파일이 줄어듭니다.
- **주의**: "검증 실패"가 나오면 다음 묶음을 진행하지 않습니다. 남은 파일, 함께 지워진 파일, 깨진 참조, 본문 변경 중 무엇 때문인지 확인합니다.

### 8. 검토와 병합

- **진행**: 에이전트가 삭제한 개수와 용량, 남은 파일을 보고합니다. 도구에는 병합 기능이 없습니다.
- **사용자가 할 일**: GitBook의 Changes 화면에서 확인하고 **직접 병합**합니다.
- **바뀌는 것**: 병합하면 삭제가 게시본에 반영됩니다.
- **주의**:
  - 병합 전에 이상이 보이면 병합하지 않습니다.
  - 본문이 아직 쓰는 이미지는 Change Request에서 다른 이미지로 바꿨더라도 남습니다. 병합한 뒤 다시 검사하면 후보가 됩니다.
  - 삭제 확인 창은 파일 내용이 버전 기록에 남는다고 안내합니다. 복구는 시험하지 않았습니다.

### 정리를 마친 뒤

- 로그인 정보를 지우려면 스킬 폴더의 터미널에서 `node node_modules/@gitbook/cli/cli.js logout`을 실행합니다.
- 보고서가 더 필요 없으면 `gblc-reports` 폴더를 지웁니다.

## 판정 기준

검사하는 곳:

- 대상 스페이스의 본문(숨김 페이지, 운영 문서 포함), 페이지 설정과 표지, 재사용 콘텐츠
- 병합되지 않은 모든 Change Request(초안, 열림, 보관)
- 같은 조직의 다른 스페이스와 그 Change Request
- 조직의 사이트 설정(로고, 파비콘 등. 사이트 안 스페이스별 설정 포함)

| 판정 | 조건 | 삭제 |
|---|---|---|
| 사용 중 | 파일 ID 또는 업로드 주소가 원문 어디에든 있음 | 안 함 |
| 이미지 아님 | 이미지 형식이 아님 | 안 함 |
| 불확실 | 업로드 주소를 알 수 없음 | 안 함 |
| 삭제 후보 | 위에 해당하지 않는 이미지 | 승인 후 |

파일은 이름이 아니라 고유 ID로 식별합니다. 이름이 같은 파일이 여러 개여도 각각 판정합니다.

재검사와 삭제 사이에 누가 참조를 추가하면 삭제 전에는 알 수 없고, 검증에서 발견합니다.
